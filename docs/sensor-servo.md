# MG996R en la ESP32 de sensores

Recablear DATA del DHT11 de GPIO 22 a GPIO 21 (libre en este firmware: sin I²C ni otros periféricos asignados). Mantener pH en GPIO 34 y suelo en GPIO 35. Conectar señal MG996R a GPIO 22 de **sensores**. La ESP32 de movimiento y W/A/S/D permanecen independientes.

Instalar ESP32Servo en Arduino junto con las dependencias existentes. PWM 50 Hz; límites heredados 70–130°, centro 100°, pulsos 500–2400 µs. No ampliar estos valores sin calibrar físicamente pulsos, neutral y holgura. El arranque del firmware adjunta el servo y comanda 100°: mantener alimentación del actuador desconectada durante instalación/verificación. No se cargó firmware ni se accionó hardware como parte de este cambio.

Alimentar MG996R con fuente externa regulada apropiada (5–6 V, dimensionada para corriente de arranque/bloqueo del servo, con margen); no desde 3.3 V ni el regulador de la ESP32. Unir GND de fuente, servo y ESP32. Verificar polaridad y disponer de corte de alimentación independiente.

React → Spring `/sensor-servo` → cliente dedicado **servoClient** → ESP32 `/servo`. GET devuelve ángulo comandado (sin realimentación física) y estado. POST `/sensor-servo/session` adquiere una época mediante `/servo-session`; POST envía INCREASE, DECREASE, HOLD o CENTER con época y secuencia. El backend añade vencimiento relativo al reloj del dispositivo y X-Device-Token existente. Las rutas mutantes del navegador conservan CSRF. No se envía el token al navegador.

E/Q y botones giran mientras se mantienen; R centra. Soltar, perder foco, ocultar/cerrar página o desmontar envía HOLD; este invalida la época para rechazar mensajes anteriores. Renovación cada 250 ms, interpolación en firmware de hasta 2° cada 15 ms mediante millis(), sin bucles de espera. GET de estado cada 1000 ms solamente en reposo; al iniciar control se cancela la consulta pendiente y se ignoran respuestas anteriores. Pérdida de Wi-Fi o 1000 ms sin comandos detiene e invalida el control; consultar estado no renueva el watchdog. La parada por red depende de la latencia, con watchdog como respaldo; HOLD mantiene PWM/posición, no corta corriente. Durante el control se sirven capturas de caché vigentes; si hace falta una lectura nueva, `/capture` devuelve 503 hasta liberar el control, sin presentar una muestra vieja como nueva.


## Latencia y validación (sin hardware)

- Wi-Fi sin ahorro de energía; se retiraron las ocho lecturas ADC y escrituras Serial de diagnóstico periódicas. `servoTick()` se ejecuta antes y después de HTTP. DHT11 sigue siendo síncrono, pero no se inicia una adquisición durante una sesión activa. Una adquisición ya iniciada antes de recibir control aún puede retrasarlo.
- Un comando de giro en vuelo; renovación a partir de 250 ms entre envíos, sin acumular peticiones. Cambios de dirección reutilizan la sesión y conservan solo la intención más reciente. HOLD se envía inmediatamente al liberar, aunque siga pendiente un ACK; no se espera a que abortar fetch cancele el trabajo remoto. Una adquisición tardía se cierra con HOLD. No se abre otra sesión hasta resolver adquisición/comando y HOLD anteriores.
- Cliente servo: conexión 250 ms, lectura 600 ms; navegador conserva 1200 ms. Son presupuestos de fallo, no mediciones de Wi-Fi. Se eligieron por debajo del watchdog de 1000 ms y del límite de vigencia de 750 ms; las capturas conservan su timeout. Una red que tarde segundos se rechaza en vez de ampliar la ventana de movimiento. HTTP/1.1 explícito evita negociación HTTP/2 con los WebServer de ESP32.
- El reloj del dispositivo se ancla al recibir la adquisición: usar el instante de envío sumaba indebidamente su RTT al deadline. Se conserva el límite de 750 ms, secuencia, época, propiedad de sesión y watchdog de 1000 ms. HOLD invalida la época; paquetes viejos no pueden reactivar el giro.
- Diagnóstico: `performance.getEntriesByType('measure').filter(e => e.name.startsWith('servo:'))` muestra el último tiempo de adquisición, comando o HOLD hasta ACK/error, incluida protección CSRF si fue necesaria. `Server-Timing: servo;dur=…` mide el procesamiento de la ruta backend, incluida espera del dispositivo. Activar DEBUG de `ServoService` registra RTT del dispositivo sin tokens. Restar duraciones permite aproximar transporte/overhead, no separar exactamente cada tramo de red. Un ACK contiene ángulo comandado, nunca posición física medida.
- Interpolación intacta: hasta 2° cada 15 ms; 30° requieren nominalmente 225 ms y 60° 450 ms, más bloqueos y dinámica mecánica. HOLD conserva PWM y posición comandada; no demuestra detención mecánica instantánea.

Reproducir: `npm test --prefix frontend`, `npm run lint --prefix frontend`, `npm run build --prefix frontend`, `JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 ./mvnw -B verify`, `scripts/test-firmware.sh`. Maven abre únicamente servidores HTTP mock en loopback para estas pruebas. Tests cubren ACK de 30/300/900/4000 ms, liberación durante adquisición, desmontaje, timeout, cambio de dirección pendiente, prioridad HOLD, paquete vencido, watchdog, Wi-Fi y control W/A/S/D independiente. El ensayo `servoBudgetBoundsSlowAck` compara el presupuesto previo de lectura (5 s) con 600 ms ante un ACK artificial retrasado 4 s: mide espera hasta respuesta/error, no mejora de movimiento físico. Ejecución local del 2026-11-11: presupuesto previo devolvió ACK a 4002,3 ms; presupuesto nuevo produjo timeout a 601,9 ms. Resultado: 106 tests frontend aprobados; Maven 56 tests, 51 aprobados y 5 omitidos (4 PostgreSQL y 1 ensayo opcional de latencia de movimiento); lint, build y mocks de ambos firmwares aprobados.
